Every partition is copied to `replication.factor` brokers: one leader takes all writes, and followers pull from it. The in-sync replica set (ISR) decides when a write counts as committed, which replicas can become leader, and how far consumers can read.

## How it works

Followers fetch from the leader like consumers do, so their logs have the same offsets in the same order. A replica is **in sync** while its broker keeps its session with the controller (KRaft heartbeats, `broker.session.timeout.ms`) and it keeps up with the leader. A follower that has not fetched, or not caught up to the leader's log end offset, for `replica.lag.time.max.ms` (default 30000 ms) is dropped from the ISR. The test is time, not a message count.

A record is **committed** once every ISR member has it. The **high watermark** (HW) is the offset after the last committed record. Consumers only read below the HW; anything between the HW and the leader's **log end offset** (LEO) could still be lost.

**Durability knobs.** Producer `acks=all` waits for the current ISR. Topic `min.insync.replicas` (default 1) is the smallest ISR that may accept an `acks=all` write; below it the producer gets `NotEnoughReplicas` or `NotEnoughReplicasAfterAppend`. The usual setup is RF 3, `min.insync.replicas=2`, `acks=all`: one broker can be down and writes still succeed with two copies.

**Leader election.** In KRaft the active controller notices a failed broker and picks a new leader from the remaining ISR, batching elections for many partitions. With f+1 replicas, Kafka tolerates f failures without losing committed data. If every ISR member is down, `unclean.leader.election.enable` (default `false`) decides: wait for an ISR member (consistency) or let an out-of-sync replica lead and lose what it missed (availability). `auto.leader.rebalance.enable` (default `true`) later moves leadership back to the preferred replica.

**KRaft controllers.** Metadata lives in the `__cluster_metadata` log, replicated across a controller quorum. A majority must be up: 3 controllers survive 1 failure, 5 survive 2 (2N+1). `process.roles` is `broker`, `controller` or both ("combined", for development only), and every node sets `controller.quorum.bootstrap.servers`.

## Gotchas the exam loves

- `acks=all` means "all **current** ISR members", not all assigned replicas. RF 2 with `min.insync.replicas=1` keeps accepting writes on a single copy.
- `min.insync.replicas` only affects producers using `acks=all`.
- `min.insync.replicas` equal to RF means any single broker outage blocks `acks=all` writes.
- When writes are refused for too small an ISR, reads of committed data still work: the partition still has a leader.
- The replication factor includes the leader. It can't exceed the number of brokers; topic creation fails.
- Broker defaults `default.replication.factor` and `num.partitions` are both 1. `offsets.topic.replication.factor` and `transaction.state.log.replication.factor` default to 3.
- `endOffsets()` for a `read_uncommitted` consumer returns the high watermark; for `read_committed` it returns the LSO.
- Unclean election trades data loss for uptime. It never lets consumers read above the HW.

## Java sample

```java
try (Admin admin = Admin.create(Map.of("bootstrap.servers", "localhost:9092"))) {
    NewTopic orders = new NewTopic("orders", 6, (short) 3)
        .configs(Map.of(
            "min.insync.replicas", "2",
            "unclean.leader.election.enable", "false"));
    admin.createTopics(List.of(orders)).all().get();

    TopicDescription d = admin.describeTopics(List.of("orders"))
        .allTopicNames().get().get("orders");
    d.partitions().forEach(p ->
        System.out.printf("p%d leader=%s isr=%s%n", p.partition(), p.leader(), p.isr()));
}
```

Kafka 4.x also applies a "strict min ISR" rule: the high watermark does not advance while the ISR is smaller than `min.insync.replicas`, whatever the producer's `acks`. Eligible Leader Replicas (KIP-966), on by default for new clusters from 4.1, let the controller elect some safe replicas outside the ISR.</Note>
