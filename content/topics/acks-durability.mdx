The producer's `acks` setting decides when a write counts as successful. On its own, `acks=all` only means "every replica that is in sync right now". `min.insync.replicas` on the topic turns that into a real durability guarantee by setting a floor on how many replicas that must be.

## How it works

Each partition has a leader and followers. Followers that keep up with the leader form the in-sync replica set (ISR). A follower drops out of the ISR if it hasn't fetched up to the leader's log end for `replica.lag.time.max.ms` (default 30000).

- `acks=0`: the record goes into the socket buffer and counts as sent. There's no response, so `retries` does nothing and the offset in `RecordMetadata` is `-1`.
- `acks=1`: the leader writes to its own log and replies. If it dies before a follower copies the record, the record is lost even though the producer got a success.
- `acks=all` (same as `-1`, and the default): the leader waits until every current ISR member has the record.

When `acks=all` arrives and the ISR has fewer than `min.insync.replicas` members, the leader refuses the write with `NotEnoughReplicasException`. If the ISR shrinks after the record was appended, the error is `NotEnoughReplicasAfterAppendException`. Both are retriable, so the producer keeps retrying until `delivery.timeout.ms` runs out.

The standard durable setup is `replication.factor=3`, `min.insync.replicas=2` and `acks=all`. It survives one broker loss with no data loss and keeps accepting writes.

## Gotchas the exam loves

- The `acks` default has been `all` since Kafka 3.0. Valid values are `all`, `-1`, `0` and `1`.
- The `min.insync.replicas` default is `1`, both as a topic config and as the broker default. With 1, `acks=all` can succeed when only the leader has the record.
- `min.insync.replicas` is a minimum ISR size, not a number of acks. With three replicas in the ISR, `acks=all` waits for all three, even if `min.insync.replicas=2`.
- `min.insync.replicas` only blocks writes for `acks=all` producers. An `acks=1` producer still gets acknowledgements when the ISR is too small.
- The 4.4 docs add that, whatever the `acks` setting, records aren't visible to consumers until they're on all in-sync replicas and the `min.insync.replicas` condition is met.
- `min.insync.replicas` equal to `replication.factor` means any single broker outage stops `acks=all` writes.
- `NotEnoughReplicasAfterAppendException` means the record may already be in the log, so a retry can duplicate it unless idempotence is on.
- `unclean.leader.election.enable` defaults to `false`. Turning it on lets an out-of-sync replica become leader and lose committed records.
- There is no producer config called `min.insync.replicas`. It's set on the topic, or as a broker or cluster default.

## Java sample

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.ACKS_CONFIG, "all"); // the default, stated for clarity

try (Producer<String, String> producer = new KafkaProducer<>(props)) {
    producer.send(new ProducerRecord<>("payments", "acct-42", "debit:100"), (md, e) -> {
        if (e != null) {
            // A NotEnoughReplicas error is retried inside the client, so it
            // only shows up here once delivery.timeout.ms has run out.
            log.error("send failed", e);
        } else {
            log.info("written to {}-{} at offset {}", md.topic(), md.partition(), md.offset());
        }
    });
}
```

## Version notes

- Kafka 3.0 changed the `acks` default from `1` to `all`.
- Kafka 4.x adds Eligible Leader Replicas (KIP-966). ELR is on by default for new clusters from 4.1. With ELR enabled, `min.insync.replicas` must be set at cluster level rather than per broker, and the leader election rules change.
