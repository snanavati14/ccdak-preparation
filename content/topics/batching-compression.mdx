`send()` doesn't put anything on the network. It serializes the record, picks a partition, and adds the record to a per-partition batch in memory. A background I/O thread sends the batches. `batch.size` and `linger.ms` decide when a batch leaves, compression works on whole batches, and `buffer.memory` with `max.block.ms` decide what happens when the producer can't keep up.

- **Batching.** Each partition has an open batch of up to `batch.size` bytes (default 16384). The batch is sent once it's full, or after `linger.ms` (default 5) if it isn't. One request to a broker can carry batches for several partitions, up to `max.request.size` (default 1048576).
- **Compression.** `compression.type` (default `none`; also `gzip`, `snappy`, `lz4`, `zstd`) compresses whole batches, so fuller batches compress better. The broker decompresses batches to validate them, stores them compressed, and consumers decompress them.
- **Back-pressure.** `buffer.memory` (default 33554432, 32 MB) caps the memory used for unsent records. When it's full, `send()` blocks. After `max.block.ms` (default 60000) it fails with `BufferExhaustedException`, a subclass of `TimeoutException`.

## Gotchas the exam loves

- `linger.ms` changed from 0 to 5 in Kafka 4.0. Older material, and even parts of the `KafkaProducer` javadoc, still describe 0.
- A batch is sent when it reaches `batch.size` *or* `linger.ms` passes, whichever comes first. Under heavy load, batches fill before the linger time is up.
- `batch.size=0` turns batching off. A record bigger than `batch.size` isn't rejected; it gets a batch of its own.
- The size limits are `max.request.size` on the producer and `max.message.bytes` on the topic (broker default `message.max.bytes`, 1048588). A record over the limit fails with `RecordTooLargeException`, which isn't retried.
- `max.block.ms` covers the wait for metadata and the wait for buffer space inside `send()`. Time spent in your serializer or partitioner doesn't count.
- If a topic is missing and auto-creation is off, `send()` waits up to `max.block.ms` for metadata, then the send fails with a `TimeoutException`.
- The topic-level `compression.type` defaults to `producer`, which keeps the producer's codec. Any other value makes the broker recompress into that codec.
- `flush()` makes every buffered record sendable at once and blocks until they all complete. Calling it from a `send()` callback throws an exception in 4.1 and later.

## Java sample

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
// Throughput tuning: bigger, fuller batches, compressed on the wire.
props.put(ProducerConfig.BATCH_SIZE_CONFIG, 64 * 1024);
props.put(ProducerConfig.LINGER_MS_CONFIG, 20);
props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");
props.put(ProducerConfig.MAX_BLOCK_MS_CONFIG, 10_000);

try (Producer<String, String> producer = new KafkaProducer<>(props)) {
    for (int i = 0; i < 10_000; i++) {
        producer.send(new ProducerRecord<>("clicks", "user-" + (i % 100), "{\"page\":\"/home\"}"));
    }
    producer.flush(); // push out anything still lingering, wait for completion
}
```

## Version notes

- Kafka 4.0 changed the `linger.ms` default from 0 to 5.
- Kafka 4.1 made `flush()` detect calls from inside a `send()` callback and refuse them, because they could deadlock.
