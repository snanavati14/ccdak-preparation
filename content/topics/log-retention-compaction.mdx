Each partition is a directory of segment files, and all cleanup works on whole segments. `cleanup.policy` picks the cleanup: `delete` drops old segments by time or size, `compact` keeps at least the latest record per key, and `delete,compact` does both.

## How it works

**Segments.** A partition directory such as `orders-0` holds segment files named after the first offset they contain (`00000000000000000000.log`, ...). Writes always go to the last one, the **active segment**. It rolls when it reaches `segment.bytes` (default 1 GiB) or gets older than `segment.ms` (default 7 days). The active segment is never compacted.

**Delete policy.** A closed segment goes once its **largest** record timestamp is older than `retention.ms` (default 604800000, 7 days), or once the partition is over `retention.bytes` (default -1, no limit; oldest segments go first). Either condition is enough. `retention.bytes` is **per partition**, so multiply by the partition count for the topic total. The broker checks every `log.retention.check.interval.ms` (default 5 minutes).

**Compact policy.** The log cleaner copies closed segments and drops any record whose key appears again later. Offsets never change and order is kept, so a compacted log has gaps in its offsets. A record with a key and a `null` value is a **tombstone**: it removes the key, and it is itself removed after `delete.retention.ms` (default 86400000, 1 day).

When the cleaner runs:

- `min.cleanable.dirty.ratio` (default 0.5): clean once at least this share of the log is uncompacted. Higher means fewer, cheaper cleanings but more duplicate data on disk.
- `min.compaction.lag.ms` (default 0): a record stays uncompacted at least this long.
- `max.compaction.lag.ms` (default `Long.MAX_VALUE`): a record becomes eligible after this long even if the dirty ratio isn't met. For compacted topics the active segment also rolls at the smaller of `segment.ms` and this value.

## Gotchas the exam loves

- Retention deletes whole segments, never single records. A segment stays until its newest record expires.
- In 4.4 a `retention.ms` breach rolls the active segment so it can be deleted; it is not compacted while active.
- "Old values still visible on a compacted topic" usually means they are in the active segment. Lower `segment.ms` or set `max.compaction.lag.ms`.
- Compaction guarantees **at least** the latest value per key, not exactly one.
- A consumer that takes longer than `delete.retention.ms` to read from the start can miss tombstones and keep deleted keys.
- `delete,compact` compacts what retention keeps; keys can still age out.
- Topic settings override broker defaults (`log.retention.ms`, then `log.retention.minutes`, then `log.retention.hours` = 168).
- An empty `cleanup.policy` means keep everything.

## Java sample

```java
try (Admin admin = Admin.create(Map.of("bootstrap.servers", "localhost:9092"))) {
    NewTopic profiles = new NewTopic("customer-profiles", 6, (short) 3)
        .configs(Map.of(
            "cleanup.policy", "compact",
            "min.compaction.lag.ms", "3600000",   // keep every update for 1 hour
            "delete.retention.ms", "604800000",   // keep tombstones 7 days
            "segment.ms", "86400000"));           // roll daily so compaction can run
    admin.createTopics(List.of(profiles)).all().get();
}
// Delete a key: send a tombstone.
producer.send(new ProducerRecord<>("customer-profiles", "cust-42", null));
```
